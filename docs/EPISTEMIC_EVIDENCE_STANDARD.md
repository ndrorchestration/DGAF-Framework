# DGAF Epistemic Evidence Standard

**Status:** Canonical repository-local standard  
**Effective:** 2026-08-16  
**Repository:** `ndrorchestration/DGAF-Framework`

## Purpose

This document prevents implementation, testing, deployment, formal analysis, synthetic evaluation, runtime observation, and real-world efficacy from being conflated.

## Canonical evidence ladder

| Status | Meaning | Minimum evidence |
|---|---|---|
| `DEFINED` | Concept/specification exists and is version-controlled. | Source/specification artifact. |
| `IMPLEMENTED` | Code/configuration exists and is wired for the stated scope. | Source plus structural/integration inspection. |
| `TESTED` | Deterministic automated tests exercise the stated behavior. | Reproducible test command and result. |
| `VERIFIED` | The exact claim has reproducible execution evidence with retained output. | Current commit/ref, environment, command, output/artifact. |
| `ATTESTED` | A dated observation or provenance trace establishes that a state/event occurred. | Timestamped trace, deployment record, or equivalent provenance. |
| `VALIDATED` | Independent evidence supports fitness for the intended use under defined conditions. | Independent protocol/data/environment and observed outcome. |
| `EMPIRICALLY SUPPORTED` | Real workload or observational evidence supports a performance/efficacy claim. | Real workload data, protocol, metrics, repetitions, and limitations. |

Higher states do not automatically imply every lower state for every claim; the evidence must match the claim's scope.

## Non-equivalences

- Deployment readiness is not runtime integration verification.
- A passing unit test is not real-world efficacy.
- Synthetic fixtures are not real-workload performance.
- Testing an evaluator does not validate the system being evaluated.
- A formal model existing is not formal verification.
- A successful bounded TLC/model-checking run is not an unbounded mathematical proof.
- Historical success is not current-state evidence unless the relationship to the current commit/ref is established.
- Absence of evidence is not evidence of absence.
- A numerical target is an acceptance criterion or hypothesis until measured.

## Required evidence record

Any claim promoted beyond `IMPLEMENTED` should identify:

1. **Exact claim** — what is being asserted.
2. **Scope and assumptions** — what the evidence does and does not cover.
3. **Source commit/ref** — the code/specification state evaluated.
4. **Execution or observation method** — exact command, protocol, or observation path.
5. **Environment/toolchain** — runtime versions and material dependencies.
6. **Data/fixture provenance** — hashes or source identification where applicable.
7. **Retained output** — machine-readable artifact, log, trace, or equivalent.
8. **Evidence class** — synthetic, deterministic, formal, runtime, empirical, etc.
9. **Limitations** — known boundary conditions and excluded claims.
10. **Falsifier/revision condition** — what result would invalidate, downgrade, or require revision.

## Formal-model claims

Formal-analysis documentation must state the actual checked scope:

- safety/invariant checking;
- liveness checking;
- bounded state-space exploration;
- parameter-bounded model checking; or
- a justified mathematical proof.

Never convert a bounded model result into an unbounded theorem claim without an explicit argument establishing that scope.

## Synthetic evaluation

A deterministic evaluator passing repository-authored fixtures establishes the correctness/reproducibility of the evaluator and fixture protocol within that scope. It does not establish model capability unless predictions are actually generated by the evaluated system and independently scored.

## Runtime and deployment

A deployment marked ready, healthy, or published does not prove an end-to-end transaction. Runtime claims require an observed request/event path with dated provenance, relevant commit/ref, and retained output.

## Historical evidence

Historical evidence remains useful and must remain visible, but it must be labeled historical. It cannot silently become present-tense evidence for `main` or another ref.

## Claim-language policy

Prefer precise terms such as:

`implemented` · `tested` · `bounded model-checked` · `synthetic demonstration` · `runtime evidence pending` · `attested` · `validated` · `empirically supported`

Do not use `proven`, `production-ready`, `validated`, `verified`, or percentage efficacy claims merely as rhetorical substitutes for missing evidence.

## Closure rule

An implementation or documentation change cannot close an empirical evidence gate by itself. An issue closes only when its explicit evidence condition is satisfied or a newer authoritative decision supersedes it.
